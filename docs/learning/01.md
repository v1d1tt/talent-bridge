# Slice 01: Walking skeleton

**What was built:** the thinnest working path through every layer. A Solid page calls the Go server, the Go server checks Postgres, and the whole thing ships as one Docker image to Azure Container Apps. Every push is tested by CI. Nothing about cricket works yet; that is on purpose. A walking skeleton proves the pipes before the features.

## 1. How a request flows

Open `/settings` in the browser:

1. **Browser → Go.** The Go server ([internal/server/server.go](../../internal/server/server.go)) gets `GET /settings`. No file has that name and the path has no extension, so `spa()` sends `web/dist/index.html`. (A missing `/assets/x.js` gets a real 404 instead, so a stale page does not silently load HTML as JavaScript.)
2. **Page starts.** [web/src/main.tsx](../../web/src/main.tsx) calls `render(() => <App />)` from `@solidjs/web`. [App.tsx](../../web/src/App.tsx) builds the router with `createRouter` and the router picks the `Settings` component for `/settings`.
3. **Page → API.** In [pages/Settings.tsx](../../web/src/pages/Settings.tsx), `createMemo(() => fetchHealth())` is an **async memo**: in Solid 2 a memo may return a promise. `<Loading>` shows "Checking…" until it settles; `<Errored>` shows "server not reachable" if it throws. [health.ts](../../web/src/health.ts) turns the HTTP answer into a typed `HealthReport` (a 503 is still a report: the server answered, the database did not).
4. **Go → Postgres.** `GET /api/health` runs `health.Handler` ([internal/health/health.go](../../internal/health/health.go)), which calls `Probe` on the database ([internal/database/database.go](../../internal/database/database.go)). `Probe` makes sure the migrations ran, then runs a real query (`CountUsers`, generated by sqlc from [db/queries/users.sql](../../db/queries/users.sql)).
5. **Back to the page.** The handler answers `200 {"status":"ok", "database":{"status":"up", ...}}` or `503 {"status":"degraded", ...}`. The error text goes only to the server log; the client never sees connection details.
6. **Check again** increments a signal that the async memo reads, so the memo re-runs `fetchHealth`. While it runs, `isPending(report)` is true and the button says "Checking…", but the old sheet stays on screen (Solid 2 holds the last committed value).

## 2. The database parts

- **goose** ([db/migrations/00001_create_users.sql](../../db/migrations/00001_create_users.sql)) holds numbered SQL files with an `Up` and a `Down` part. The files are compiled into the binary with `//go:embed` ([db/embed.go](../../db/embed.go)), so the Docker image needs no extra files.
- **Migrations run at start-up**, inside the server, through a goose `Provider` with a **Postgres session advisory lock**. If the host starts two instances at once, the second waits for the lock, so a migration never runs twice. A test fires 8 probes at once to check this.
- **Why the direct Neon URL, not the pooled one:** an advisory lock belongs to one database session. A transaction-mode pooler (PgBouncer) hands each statement to any session, so the lock would not hold.
- **sqlc** reads the migrations (as the schema) and the queries, and writes Go code into `internal/store`. If the SQL is wrong, `sqlc generate` fails, not production. CI runs `sqlc diff` to catch generated code that is out of date.
- **pgx pool** is created without connecting. So the server starts (and shows a red status) even when Neon is asleep or down; the first query connects. `MaxConns = 4` per instance keeps far below Neon's connection limit.
- **`users.id` is a `uuid`**, not a counter: ids will appear in profile URLs later, and a counter would let anyone guess every id. Slice 2 adds the sign-in columns in migration 2.

## 3. CI for someone new to it

**Continuous integration** means a robot runs your checks on every push, on a clean machine, so "works on my laptop" is not the test. GitHub Actions reads [.github/workflows/ci.yml](../../.github/workflows/ci.yml):

- `on:` says when: every push to `main` or `slice/*`, every pull request.
- A **job** is a list of **steps** on a fresh Ubuntu machine. `uses:` runs a published action (for example `actions/setup-go` installs Go); `run:` runs a shell command.
- `services: postgres` starts a real Postgres container next to the job, so the Go database tests and the Playwright test use a real database, not a mock.
- The job **Lint and test** is a **required status check** on `main`: GitHub will not merge a pull request until it is green. With auto-merge on, the PR merges itself the moment it turns green.
- On failure, Playwright's trace (a step-by-step recording of the browser) is uploaded as an artifact you can download from the run page.

The three test layers, from fast to slow:

| Layer | Tool | Checks | Example |
|---|---|---|---|
| Go unit + integration | `go test` | handler answers, routing, migrations against real Postgres | [server_test.go](../../internal/server/server_test.go) |
| Page components | Vitest + Solid Testing Library (jsdom) | each status state renders the right words | [App.test.tsx](../../web/src/App.test.tsx) |
| End to end | Playwright (real Chromium) | real browser → real Go server → real Postgres, and no console errors | [smoke.spec.ts](../../web/e2e/smoke.spec.ts) |

The smoke test also fails on any console error. That caught a real bug in this slice: after the font packages were removed, `main.tsx` still imported one; Vite built anyway and the page was blank.

## 4. Docker for someone new to it

A **Docker image** is a packaged file system plus a start command: whatever runs it gets exactly the same program. The [Dockerfile](../../Dockerfile) has three **stages**; only the last one ships:

1. `node:24-alpine` installs npm packages and runs `vite build` → `web/dist`.
2. `golang:1.27-alpine` builds one static binary (`CGO_ENABLED=0`, so it needs no C libraries). `-ldflags "-X main.version=..."` writes the git commit into the binary; the Settings page shows it as "Build".
3. `gcr.io/distroless/static-debian12:nonroot` (a Google-made base image; it runs on any host) gets only the binary and `web/dist`. It has no shell and no package manager, and runs as a non-root user: less to attack, and the image is about 23 MB.

`.dockerignore` keeps `.env`, `node_modules`, `.git` and docs out of the build context, so a secret can never be copied into an image by accident.

## 5. Azure Container Apps for someone new to it

**Azure Container Apps** runs a container image and gives it an HTTPS URL. It starts containers (called **replicas**) when requests come and stops them when idle. The plan first used GCP Cloud Run, which works the same way; the GCP billing sign-up failed, so the host moved to Azure for Students, which needs no card ([ADR 0006](../adr/0006-azure-container-apps-host.md)). The Docker image did not change at all: that is the point of a container.

- **Region:** Azure for Students allows only 5 regions. The app runs in Malaysia West (Kuala Lumpur), about 300 km from the Neon database in Singapore, so each database call adds only a few milliseconds.
- **min replicas 0:** no traffic → no running container → no cost. The price is a **cold start**: the first request waits while a replica starts (and Neon wakes, too). The page says "the first check can take a few seconds".
- **max replicas 2, 0.25 vCPU, 0.5 GiB:** a hard cap on cost and on database connections. The monthly free grant (180,000 vCPU-seconds, 2 million requests) covers this app.
- The app listens on port 8080; the deploy sets `--target-port 8080`, and Azure's HTTPS front end forwards to it. On shutdown the container gets `SIGTERM`; [main.go](../../cmd/server/main.go) stops taking new requests and finishes the open ones within 8 s.
- **Logs:** the server writes one JSON object per line with `severity` and `message`. Container Apps sends stdout to a Log Analytics workspace, where the JSON fields can be queried.
- **Secrets:** `DATABASE_URL` is a GitHub Actions secret. Each deploy copies it into a **Container Apps secret** (`database-url`), and the container reads it through `DATABASE_URL=secretref:database-url`. It is never in the image or the repo.
- **Image registry:** the image goes to GitHub Container Registry (`ghcr.io`), which is free for public images. Azure pulls it with no password, so the package must be public.

### How GitHub deploys without a key (OIDC federation)

Old way: create a service principal with a client secret (or a JSON key) and paste it into GitHub secrets. If it leaks, anyone can deploy until someone notices. New way:

1. The deploy job has `permissions: id-token: write` and `environment: azure`, so GitHub can sign a short-lived **OIDC token** whose subject is `repo:v1d1tt@214258466/talent-bridge@1164844077:environment:azure`. The numbers are the owner and repo IDs. GitHub adds them so that if this repo were deleted or renamed and someone else took the name, their tokens would not match. (Older guides show the subject without IDs; the first deploy failed with `AADSTS700213: No matching federated identity record` until the credential used the exact subject from the failed run's log.)
2. `azure/login` sends that token to Microsoft Entra ID. A **user-assigned managed identity** (`github-deploy`) has a **federated credential** that trusts exactly that issuer (`token.actions.githubusercontent.com`) and that subject.
3. Entra ID returns a short-lived Azure token for the identity. It has the Contributor role on the `talent-bridge` resource group only, so it can deploy this app and nothing else in the subscription.

Nothing long-lived exists to leak. (GCP calls the same idea "Workload Identity Federation"; AWS calls it "IAM OIDC identity provider".)

### Preview deploys (revisions and two apps)

Each deploy creates a **revision**: an unchangeable snapshot of image + settings, named `<app>--c<sha7>-<attempt>`. The app runs in **single revision mode**: the newest healthy revision gets all traffic and the old one is switched off.

- A push to `main` deploys the live app, `talent-bridge`.
- A push to `slice/01-walking-skeleton` deploys the same image to a second app, `talent-bridge-preview`, with its own URL. So the slice is checked live before merge, while the live app keeps serving the old version. Both apps scale to zero, so the preview costs nothing while idle.
- The first plan was one app in **multiple revision mode**, with a **label** (`slice-01`) giving the preview revision its own URL. Azure refused it: `ExpressMultiRevisionModeNotSupported`. The environment Azure created is an *express* environment (a simpler preview offering), which allows only single revision mode. Two apps give the same result with no extra feature.

## 7. Questions an interviewer could ask

**Q: Why run migrations inside the server instead of a separate CI step?**
A: The image then carries its own schema, so a rollback to an old image never runs against a schema it does not know about, and there is no extra job holding database credentials. The risk is two instances migrating at once; a Postgres advisory lock (goose session locker) makes them take turns, and a test hits it with 8 concurrent probes. For long migrations or many instances I would move to a Container Apps job that runs before the deploy.

**Q: Your health check returns 503 when the database is down. Doesn't that make the host restart the container?**
A: No. Container Apps' default probes are TCP checks on the target port, and `/api/health` is not wired as a liveness probe. That is on purpose: restarting the container cannot fix Neon being down, and it would hide the problem. The 503 is for humans and monitors; the page still loads and explains what is wrong.

**Q: How does GitHub deploy to Azure without a stored key?**
A: OIDC federation. GitHub signs a short-lived OIDC token for the workflow run; Microsoft Entra ID checks the issuer and that the token's subject is this repo's `azure` environment, then issues a short-lived token for a managed identity that may only touch one resource group. No long-lived secret exists, so there is nothing to leak or rotate. It is the same idea as GCP's Workload Identity Federation, which the first plan used.
