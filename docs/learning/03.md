# Slice 03: Browser pose → saved analysis with key frames

**What was built:** an athlete picks or records a clip. The browser runs MediaPipe Pose Landmarker on every 1/30 s of it, draws the stick figure live over the video, and builds the pose sequence (33 landmarks per frame). The server checks the sequence, stores it compressed in Postgres, and hands out signed URLs. The browser uploads 3 still JPEGs straight to Azure Blob Storage with them. The result page shows the stick figure plate, the clip's numbers and the key frames. **The clip itself never leaves the device**: a Playwright test records every request of the whole flow and checks that none carries video bytes.

There is no score yet. Scoring is slice 5; the page says so.

## 1. The flow, file by file

**In the browser**

1. **`/analyses/new`** → [pages/NewAnalysis.tsx](../../web/src/pages/NewAnalysis.tsx). Two file inputs: "Record a clip" has `capture="environment"` (the phone opens its camera), "Choose a clip" opens the gallery. The page is a small state machine: `idle → loading → reading → saving → (navigate)` or `failed`.
2. **`openClip(file)`** ([pose/extract.ts](../../web/src/pose/extract.ts)) puts the file in a hidden `<video>` through `URL.createObjectURL`: a `blob:` URL that only this tab can read. It refuses clips under 1 s or over 10 s. (iOS Safari draws no frames from a video that never played, so it plays and pauses it once, muted.)
3. **`loadLandmarker()`** ([pose/landmarker.ts](../../web/src/pose/landmarker.ts)) is imported lazily, so the 150 KB MediaPipe JavaScript and the WebAssembly runtime download only on this page. It loads the model from **our own origin** (`/mediapipe/...`), tries the GPU (WebGL) and falls back to the CPU.
4. **`extractPose(video, model, onFrame)`** seeks the video to frame *i*/30 s, waits for `seeked`, and calls `detectForVideo(video, timestamp)`. VIDEO mode tracks the body from frame to frame, so timestamps must only grow; `Loaded.nextTimestampMs` keeps counting across clips. Each frame becomes 33 × `[x, y, visibility, world_x, world_y, world_z]`, rounded to 5 decimals and clamped to the ranges the server accepts. A frame with no person is all zeros. `onFrame` updates the progress bar and draws the stick figure ([pose/skeleton.ts](../../web/src/pose/skeleton.ts), `drawSkeleton`) on a canvas over the video.
5. **`pickKeyFrames(frames, 3)`** ([pose/keyframes.ts](../../web/src/pose/keyframes.ts)): the 3 moments of most body movement (summed world-space speed of the visible landmarks, smoothed over 5 frames), at least 1/6 of the clip apart; evenly spaced if nothing moves. Phases (release, contact) come in slice 5, and the result page says how these were picked.
6. **`createAnalysis(seq, keys, csrf)`** ([analyses.ts](../../web/src/analyses.ts)) → `POST /api/analyses` with the CSRF header.

**On the server**

7. **`Guard(Roles(athlete))`** ([internal/auth/access.go](../../internal/auth/access.go)): signed in, CSRF token, athlete role (slice 2).
8. **`analysis.Service.Create`** ([internal/analysis/analysis.go](../../internal/analysis/analysis.go)):
   - Decodes the JSON through `http.MaxBytesReader` (4 MiB → 413) with `DisallowUnknownFields` (a stray `"video"` field → 400).
   - **`pose.Validate`** ([internal/pose/pose.go](../../internal/pose/pose.go)) → 422 with a reason code and a plain-English message (table below).
   - Checks the key frame indexes (2-3, inside the clip, no repeats), then the daily limit (30 analyses per athlete per 24 h → 429).
   - **`pose.Encode`** ([internal/pose/codec.go](../../internal/pose/codec.go)) → the compact stored form (section 4).
   - One database transaction (`database.DB.Tx`): `CreateAnalysis`, then one `CreateKeyFrame` row per key frame with the path `analyses/<analysis id>/<frame>.jpg` (random ids only: no user id, no name).
   - **`blob.Store.UploadURL`** ([internal/blob/blob.go](../../internal/blob/blob.go)) signs one SAS URL per key frame → `201 {"id", "key_frames": [{frame_index, upload_url, expires_at}]}`.

**Back in the browser**

9. **`cutJpeg(video, frame)`** seeks to the frame, draws it on a canvas at most 640 px wide and encodes a JPEG (quality 0.85). A canvas re-encode also drops all metadata, such as the phone's GPS position.
10. **`uploadKeyFrame(upload, jpeg)`** → `PUT <upload_url>` with `x-ms-blob-type: BlockBlob` **straight to Azure Blob Storage**. Our server never sees these bytes. The browser may do this because the storage account has a CORS rule for our two origins (PUT only).
11. **`checkKeyFrames(id)`** → `POST /api/analyses/{id}/key-frames/check` → `CheckKeyFrames` → `judge`: for each pending key frame, `blob.Store.Inspect` reads the size and the first 8 bytes. A JPEG (`FF D8 FF`) of 100 B to 512 KiB becomes `uploaded`; anything else is deleted and becomes `rejected`; a missing one stays `pending`.
12. **`navigate("/analyses/<id>")`** → [pages/Analysis.tsx](../../web/src/pages/Analysis.tsx) → `GET /api/analyses/{id}` → `Get` → `ownAnalysis` (the query has `WHERE id = $1 AND user_id = $2`, so another user's id finds no row → 404) → `writeAnalysis`: `pose.Decode`, and a fresh read SAS URL (`ReadURL`, 15 minutes) for each uploaded key frame. The page draws the plate with a frame slider, the clip sheet, and the stills in ruled cells.

**Later, on the server:** `RunSweeper` ([analysis.go](../../internal/analysis/analysis.go)) runs `Sweep` every 5 minutes. Once a key frame's upload URL has expired, nothing can write to it any more, so the sweep settles it one last time (section 6).

## 2. Why the pose model runs in the browser

([ADR 0001](../adr/0001-pose-extraction-in-the-browser.md)) Clips are large, personal and often show minors. With the model in the browser:

- **Privacy is structural, not a promise.** The server has no endpoint that accepts a video, so it cannot store one by mistake, and a breach cannot leak one.
- **No GPU server.** The phone or laptop does the heavy work. The Go server only checks numbers, which fits a 0.25 vCPU container that scales to zero.
- **The same code makes references.** The admin page (slice 4) runs the same path on pro clips, so athletes and pros are measured by the same model.

The costs: the device downloads the model once (about 4 MB of gzipped WebAssembly + the model file), and a slow phone takes longer. Also, **the server must not trust the numbers**: anyone can send a hand-made pose sequence. That is why the server validates every value, and why the score (slice 5) is computed only on the server.

The MediaPipe files are served from our own origin, not a CDN: `scripts/mediapipe.mjs` copies the WebAssembly runtime from the pinned npm package, downloads the models once (checked against pinned SHA-256 sums), writes `.gz` copies, and puts the Apache 2.0 `LICENSE` and a `NOTICE` next to them (`/mediapipe/LICENSE`, `/mediapipe/NOTICE`). Self-hosting keeps the CSP at `'self'`; the only addition is `'wasm-unsafe-eval'`, which allows compiling WebAssembly but not JavaScript `eval`. The Go server sends the `.gz` copy to browsers that accept gzip (`servePrecompressed`), so the 14.7 MB runtime downloads as 4.1 MB, and caches `/mediapipe/` files for a year (the version is in the path).

## 3. The benchmark: lite vs full

`/lab/pose-benchmark` ([pages/PoseBench.tsx](../../web/src/pages/PoseBench.tsx)) runs both models on the same clip on the device and shows: load time, model time per frame (mean and 95th percentile), frames with a person, and **jitter**: the mean frame-to-frame change in landmark speed (the second difference of x and y), in thousandths of the frame size, over landmarks seen in three frames in a row. On the same clip, lower jitter means steadier tracking, which matters for DTW and phase detection.

| Device, browser | Model | Runs on | Load | Mean / frame | p95 / frame | Frames with a person | Jitter |
|---|---|---|---|---|---|---|---|
| MacBook (Apple M5), Chrome 158, bowling 78 frames | lite | GPU | 131 ms | 9.3 ms | 12.9 ms | 78 / 78 | 27.27 |
| MacBook (Apple M5), Chrome 158, bowling 78 frames | full | GPU | 93 ms | 12.8 ms | 18.0 ms | 77 / 78 | 24.46 |
| MacBook (Apple M5), Chrome 158, straight drive 50 frames | lite | GPU | 69 ms | 9.1 ms | 12.6 ms | 50 / 50 | 8.01 |
| MacBook (Apple M5), Chrome 158, straight drive 50 frames | full | GPU | 83 ms | 11.7 ms | 18.9 ms | 50 / 50 | 10.22 |
| MacBook (Apple M5), Chrome 158, pull shot 69 frames | lite | GPU | 69 ms | 9.3 ms | 12.0 ms | 69 / 69 | 11.37 |
| MacBook (Apple M5), Chrome 158, pull shot 69 frames | full | GPU | 79 ms | 12.2 ms | 19.0 ms | 69 / 69 | 9.37 |
| iPhone 16, Safari, bowling 113 frames (full 3.8 s clip) | lite | GPU | 145 ms | 11.1 ms | 15 ms | 106 / 113 | 33.59 |
| iPhone 16, Safari, bowling 113 frames (full 3.8 s clip) | full | GPU | 97 ms | 13.5 ms | 21 ms | 104 / 113 | 29.19 |
| iPhone 16, Safari, pull shot 100 frames (full 3.3 s clip) | lite | GPU | 136 ms | 10.6 ms | 14 ms | 100 / 100 | 8.19 |
| iPhone 16, Safari, pull shot 100 frames (full 3.3 s clip) | full | GPU | 95 ms | 13.4 ms | 20 ms | 100 / 100 | 7.94 |

**Pick: full.** On both devices the full model costs only 2-3 ms more per frame (about 13.5 ms on the iPhone 16, so a 3 s clip at 30 fps takes about 1.2 s of model time), far below what an athlete notices. In return it is steadier on the fast actions: jitter drops by 10-13% on the bowling clip on both devices and a little on the pull shot. The slow straight drive is the exception (8.0 against 10.2 on the Mac), where both are already steady. Steadier landmarks give cleaner joint angles and phase detection for scoring (slices 5 and 6). The cost is a larger first download (9.4 MB against 5.8 MB, cached for a year). Lite found 1-2 more frames with a person in the bowling clip's blurred delivery frames; the server needs only half the frames to have a person, so this does not change the choice. Safari rounds `performance.now()` to whole milliseconds, which is why the iPhone p95 values are whole numbers.

**Two things the real devices taught:**

- **iOS Safari ignores `preload`.** A `<video>` that never played fires no `loadeddata`, so the first version waited forever on the iPhone while desktop Chrome and Safari worked. `openClip` now waits for `loadedmetadata`, plays and pauses muted (allowed without a tap), then waits for the first frame, with a 20 s limit that turns any other stall into a clear error.
- **MediaPipe tries to send usage logs to Google** (`odml.pa.googleapis.com`). The page's CSP `connect-src` lists only our origin and the storage account, so the browser blocks the request and nothing leaves the device. This is one more reason to keep the CSP strict instead of adding broad allowances.

## 4. The stored pose sequence: format and size

Neon's free plan has 1 GB, so the sequence is stored compactly (`pose.Encode`, format `TBP1`):

1. A 14-byte header: `"TBP1"`, fps (float32), width and height (uint16), frame count (uint16).
2. Every value as a whole number of 1/10000 units (`Scale`): 0.1 px on a 1000 px video, 0.1 mm for world values. MediaPipe's own noise is far larger.
3. **Delta coding:** each value minus the same value in the frame before. A body moves little in 1/30 s, so most differences are small.
4. **Varints (zigzag):** a small number takes 1 byte, a large one more (Go's `binary.AppendVarint`).
5. **DEFLATE** (`compress/flate`, best compression) over the whole thing.

Typical size, from real clips (checked locally in Chrome):

| Clip | Frames | Stored (`pose_sequence`) | Per frame |
|---|---|---|---|
| Bowling, 2.6 s | 78 | 20.9 KB | 268 B |
| Straight drive, 1.7 s | 50 | 11.1 KB | 222 B |
| Pull shot, 2.3 s | 69 | 15.3 KB | 222 B |

So a typical clip costs about 10-25 KB in Postgres, and the longest allowed clip (600 frames) about 160 KB. On Neon's 1 GB free limit that is roughly 40,000-90,000 analyses before the pose data alone fills it. The key frame JPEGs (25-40 KB each) live in Blob Storage, not in Postgres.

`Decode` stops at a size cap (600 frames × 198 values × 10 bytes), so a damaged or hostile stored value cannot inflate to gigabytes; a test checks it with 30 MB of zeros. The GET response sends the decoded numbers as JSON (about 60 KB for a 2 s clip).

## 5. Signed URLs (SAS) vs uploading through the server

**SAS (picked):** the server signs a URL that allows one action on one blob for a few minutes; the browser talks to Blob Storage directly.

| | SAS, browser → Blob Storage | Proxy, browser → Go server → Blob Storage |
|---|---|---|
| Our bandwidth and CPU | none: bytes go straight to Azure | every byte twice through a 0.25 vCPU container |
| Request time limits | none on our side | the upload must fit our 15 s read timeout |
| Size limit | **not enforceable in the SAS**: checked after the upload (check + sweep) | easy: `MaxBytesReader` |
| Content check | after the upload (`judge`) | before storing |
| Setup | CORS rule on the storage account, a role for the app's identity | none extra |

The size limit is the real cost of SAS, so the design closes it in three places: the upload URL may only **create** (no overwrite, so a checked JPEG cannot be swapped), it expires after **10 minutes**, and after that the **sweep** deletes anything that is not a checked JPEG. A proxy would be the right choice for large or many files that must be scanned before storage; for three 50 KB stills from a signed-in athlete, SAS keeps the server simple and cheap.

**User delegation SAS, not account-key SAS.** A SAS can be signed with the storage account key or with a *user delegation key*. The account key is a password for the whole account. Here the account has **shared key access turned off**, so no key works at all. The app runs as the user-assigned managed identity `talent-bridge-app`; `Store.delegationKey` asks Azure for a delegation key (valid 2 hours, cached) with that identity, and signs with it. What a SAS can do is the *intersection* of its own permissions and the identity's roles: `Storage Blob Delegator` on the account (may ask for the key) and `Storage Blob Data Contributor` on the `key-frames` container only. Locally and in CI, Azurite (the official emulator) stands in, with its published development key; `blob.LoadConfig` accepts a key only when the storage URL and the app URL are both on localhost (the same guard as the fake Google in ADR 0007).

## 6. Security review (secure-code-guardian)

| Threat | Control | Test |
|---|---|---|
| Another user reads my analysis | owner in the SQL `WHERE`; 404, not 403, so ids cannot be probed | `TestOnlyTheOwnerCanSeeAnAnalysis` |
| A coach or admin saves analyses | `Roles(athlete)` on the route | same test, route × role table |
| Cross-site POST | CSRF token (slice 2) | same test |
| Video smuggled in the JSON | `DisallowUnknownFields`; Playwright checks every request | `TestCreateRefusesBadRequests`, `analysis.spec.ts` |
| Fake or huge pose sequence | `pose.Validate` ranges and counts, 4 MiB body cap, 30/day limit | table tests below, `TestDailyLimit` |
| Junk or huge file at an upload URL | create-only URL, 10 min, check + sweep delete | `TestUploadAndReadURLs`, `TestCheckRejectsTooLargeOrTooSmallKeyFrames`, `TestSweepSettlesKeyFramesAfterTheUploadWindow` |
| An upload URL reused for another blob | the signature covers the blob name | `TestUploadAndReadURLs` |
| Stored HTML/script served from storage | read URL forces `Content-Type: image/jpeg` | `TestUploadAndReadURLs` |
| A leaked storage key | no key exists on Azure; the dev key works only on localhost | `TestLoadConfig` |
| Zip bomb in a stored value | decompression cap | `TestDecodeStopsAtTheSizeCap` |
| Location leak in a photo | the canvas re-encode drops EXIF | (by construction) |

Two gaps found in the review and fixed in this slice: (1) a SAS cannot cap the upload size, and the check ran only if the browser asked for it; (2) after a rejected blob was deleted, its upload URL still worked until it expired. Both are closed by the sweep, which settles every key frame once the upload window has closed.

**Mutation check:** each rule was broken on purpose, one at a time, and a test had to fail: the owner `WHERE`, create-only upload URLs, read-only read URLs, the forced `image/jpeg`, unknown-field refusal, the JPEG bytes check, the size cap, the sweep's delete, the daily limit, the localhost-only dev key, the athlete-only route, and the decompression cap. The first pass found two rules no test caught (the forced `image/jpeg` and the decompression cap); both now have tests.

## 9. Questions an interviewer could ask

**Q: If the browser computes the landmarks, what stops a user from sending fake numbers to get a better score?**
A: Nothing stops them sending numbers, so the server never trusts them. It validates the shape and every range (422 with a reason), and the score is computed only on the server, against references the athlete cannot touch. A forged sequence can at worst score itself; a coach sees only scores, and the PRD's known limits say the score is a technique estimate, not proof. If it mattered more, the next steps would be plausibility checks (bone lengths that stay constant across frames) and a coach seeing the key frames next to the score.

**Q: Why signed URLs instead of uploading through your server? What did you give up?**
A: The server never handles image bytes, so a 0.25 vCPU container stays cheap and nothing depends on our request timeouts. What I gave up is control before storage: a SAS cannot cap the size or check the content. I closed that with three rules: the URL may only create (so a checked file cannot be replaced), it lives 10 minutes, and a sweep settles every key frame after that window, deleting anything that is not a checked JPEG. For big or untrusted files that must be scanned before storage, I would proxy or upload to a quarantine container.

**Q: Your app has no storage key anywhere. How does it sign a SAS?**
A: With a user delegation key. The app runs as a managed identity; Azure gives it a token, and with that it asks Blob Storage for a delegation key valid for 2 hours, which it caches. The SAS is signed with that key, and what the SAS can do is limited by both its own permissions and the identity's roles (container-scoped). Shared key access is turned off on the account, so even a leaked key would not work. If something leaks, `az storage account revoke-delegation-keys` makes every delegation key of the account (and every SAS signed with one) stop working at once; with an account key, the only fix is to rotate the key and update everything that uses it.
