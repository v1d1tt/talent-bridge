# Slice 02: Google sign-in, auth sessions, CSRF, roles

**What was built:** a user signs in with Google, gets a server-side auth session, chooses athlete or coach once, and sees their name and role in the header. Every route has an access rule, checked by one guard. State-changing requests need a CSRF token. A banned user cannot sign in. Nothing here uses a hosted auth service, so every step below is code in this repo ([ADR 0004](../adr/0004-own-sessions-and-google-sign-in.md)).

## 1. The sign-in flow, file by file

The flow is the OpenID Connect **authorization code flow** with **PKCE**, **state** and **nonce**.

1. **Browser → `/signin`.** [pages/SignIn.tsx](../../web/src/pages/SignIn.tsx) shows Google's button. It is a plain `<a href="/auth/google/start" target="_self">`: `target` stops the Solid router from handling the click, so the browser does a full page load to the server.
2. **`GET /auth/google/start` → `Service.Start`** ([internal/auth/google.go](../../internal/auth/google.go)).
   - `discover()` ([auth.go](../../internal/auth/auth.go)) loads Google's OpenID configuration once (`oidc.NewProvider`), lazily, so a cold start does not wait for Google.
   - It makes three random values: `state` and `nonce` (`crypto/rand.Text`) and a PKCE `verifier` (`oauth2.GenerateVerifier`, 32 random bytes).
   - It stores all three in a short cookie, `__Host-tb_signin` (HttpOnly, Secure, SameSite=Lax, 10 minutes).
   - It redirects (302) to Google with `state`, `nonce`, `code_challenge = BASE64URL(SHA256(verifier))`, `code_challenge_method=S256` and `prompt=select_account`.
3. **Google.** The user picks an account. Google redirects back to `PUBLIC_URL/auth/google/callback?code=…&state=…`. The cookie comes along: SameSite=Lax cookies are sent on a top-level GET navigation from another site.
4. **`GET /auth/google/callback` → `Service.Callback`** (google.go), in this order. Any failure redirects to `/signin?error=<reason>`; the details go only to the server log.
   1. Read and delete the sign-in cookie (one attempt, one use). No cookie → `expired`.
   2. `error` in the query (the user cancelled) → `cancelled`.
   3. Compare `state` with the cookie, in constant time. Different → `failed`. This stops **login CSRF**: an attacker cannot make your browser finish *their* sign-in.
   4. `oauth2.Config.Exchange(code, VerifierOption(verifier))`: a server-to-server POST to Google's token endpoint with the client secret and the PKCE verifier. Google checks `SHA256(verifier)` against the challenge from step 2, so a stolen `code` is useless without the verifier.
   5. `IDTokenVerifier.Verify(id_token)` (go-oidc): the RS256 **signature** against Google's public keys (JWKS, fetched and cached), the **issuer** (`https://accounts.google.com`), the **audience** (our client id) and the **expiry**.
   6. Compare the token's `nonce` with the cookie. go-oidc does not do this itself. This stops **token replay**: an ID token made for another sign-in attempt is refused.
   7. `UpsertGoogleUser` ([db/queries/auth.sql](../../db/queries/auth.sql)) by Google's `sub` (stable id; an email can change).
   8. Banned → delete all their sessions, redirect to `/signin?error=banned`.
   9. `syncAdmin`: a Google-verified email in `ADMIN_EMAILS` gets the admin role.
   10. **Rotate:** delete the auth session this browser had before (session fixation), clean up dead rows, then `startSession` ([session.go](../../internal/auth/session.go)).
   11. Redirect (303) to `/welcome` (no role yet) or `/`.
5. **`/welcome`.** [pages/Welcome.tsx](../../web/src/pages/Welcome.tsx) posts `{"role":"athlete"}` to `POST /api/me/role` with the CSRF token. `ChooseRole` runs `UPDATE users SET role = $2 WHERE id = $1 AND role IS NULL`: the `IS NULL` makes the choice one-time even with two tabs. `admin` is refused (422): it comes only from config.
6. **Every later request.** The page calls `GET /api/me` ([me.ts](../../web/src/me.ts), [session.tsx](../../web/src/session.tsx)) to learn the user, the role and the CSRF token. The cookie is HttpOnly, so page scripts never see the session id.

## 2. Auth sessions (and why not a JWT)

`startSession` makes 32 random bytes. The cookie gets them base64url-encoded; the `auth_sessions` table gets only `SHA256(id)`. Someone who reads the table (a backup, a SQL injection elsewhere) cannot sign in with it.

- **Cookie:** `__Host-tb_session`, `HttpOnly` (no script access, so XSS cannot steal it), `Secure` (HTTPS only; browsers count `localhost` as secure), `SameSite=Lax` (not sent on cross-site POSTs), `Path=/`, no `Domain`. The `__Host-` prefix makes the browser reject the cookie unless it has exactly those last three, so a subdomain cannot plant one.
- **Expiry:** `TouchAuthSession` finds the row only if `expires_at > now()` (absolute: 30 days after sign-in) and `last_seen_at > now() - 7 days` (idle), and sets `last_seen_at = now()` in the same statement. Both limits are checked by the database clock.
- **Sign-out** deletes the row. The session is gone at once, on every server.

**Why server-side sessions instead of a JWT in a cookie?** A JWT is checked without a database call, but it cannot be taken back before it expires. This app must ban a user and sign them out *now*, take away the admin role *now*, and sign out with a real delete. With a JWT that needs a deny-list in the database anyway, which loses the one advantage. One indexed lookup per request costs about a millisecond here. JWTs fit when many services must check the same user without sharing a database; this app is one server.

## 3. CSRF

A cross-site request forgery is another site making your browser send a request to this app, with your cookie attached. Three layers stop it:

1. **SameSite=Lax:** the browser does not send the session cookie on a cross-site POST at all.
2. **CSRF token:** each auth session has its own random token (`auth_sessions.csrf_token`). `GET /api/me` hands it to the page; the page sends it in the `X-CSRF-Token` header on every POST. `Guard` ([access.go](../../internal/auth/access.go)) refuses every method except GET, HEAD and OPTIONS without the right token (403 `csrf`), compared in constant time. Another site cannot read `/api/me` (no CORS headers), so it cannot learn the token.
3. **Custom header:** a cross-site form cannot set a custom header at all, and `fetch` with one needs a CORS preflight, which this server never allows.

## 4. Roles and deny by default

[internal/server/server.go](../../internal/server/server.go) `Routes()` is the route table: each route has a pattern, an **access rule** and a handler. `New()` wraps every handler in `Guard(rule, handler)`. The rules ([access.go](../../internal/auth/access.go)):

| Rule | Who passes |
|---|---|
| `Public` | everyone; no session lookup |
| `Optional` | everyone; the session is used if there is one (`GET /api/me` answers `{"user": null}` signed out, so a visitor's page load is not a 401 in the console) |
| `SignedIn` | any live auth session, also before the role choice |
| `Roles(...)` | a live session with one of those roles |
| `Access{}` (zero value) | **nobody**: a route someone forgot to give a rule is denied |

Guard's order: no rule → 403; no session → 401; banned → 403 and delete all their sessions; unsafe method without CSRF token → 403; wrong role → 403. Refusals are logged with the user id (never the email or a token). The admin role is also checked against `ADMIN_EMAILS` on every request, so removing an email takes effect at the next restart, not at that user's next sign-in.

## 5. Signing in without Google (tests and local)

[internal/auth/fakegoogle](../../internal/auth/fakegoogle/fakegoogle.go) is a small OpenID Connect provider: discovery, a form instead of Google's account chooser, a token endpoint that checks the client secret, the redirect URI and the PKCE verifier, and RS256 ID tokens with a JWKS endpoint. The server runs the *same* code against it; only `GOOGLE_ISSUER` differs. `LoadConfig` ([config.go](../../internal/auth/config.go)) refuses any issuer but Google unless the issuer and `PUBLIC_URL` are both on localhost, so a deployed app cannot be pointed at a fake. The reasons, and the options not taken, are in [ADR 0007](../adr/0007-fake-google-for-local-sign-in.md).

## 7. Why each library

| Library | Version | Why |
|---|---|---|
| `golang.org/x/oauth2` | 0.38.0 | The Go team's OAuth 2.0 client: `AuthCodeURL`, `Exchange`, and PKCE (`GenerateVerifier`, `S256ChallengeOption`, `VerifierOption`) built in. |
| `github.com/coreos/go-oidc/v3` | 3.21.0 | OpenID Connect on top of oauth2: discovery, JWKS fetch and cache, ID token signature, issuer, audience and expiry checks. It leaves the nonce check to the caller (done in `Callback`). |
| `github.com/go-jose/go-jose/v4` | 4.1.9 | Signs the fake Google's ID tokens and serves its JWKS. go-oidc already uses it to verify, so it adds no new code to the server. |
| Go `crypto/rand`, `crypto/sha256`, `crypto/subtle` | Go 1.27.4 | Session ids, CSRF tokens, the stored hash, constant-time comparisons. `rand.Text()` (Go 1.24+) gives 26 base32 characters (130 bits). |

## 8. Questions an interviewer could ask

**Q: Your server keeps the client secret. Why do you still need PKCE?**
A: PKCE protects the authorization code in transit through the browser. If the code leaks (a log, a browser history, a malicious extension reading the redirect URL), the attacker still needs the verifier, which never left the server's cookie and only its SHA-256 went to Google. The OAuth 2.0 Security Best Current Practice (RFC 9700) recommends PKCE for confidential clients too. `state` stops a different attack (login CSRF) and `nonce` another (ID token replay), so all three are used.

**Q: Why store only a hash of the session id? It is random, not a password.**
A: So that a read-only leak of the database (a backup, a log of a query, an injection bug elsewhere) does not hand out live sessions. The cookie holds the id; the database holds `SHA256(id)`. A fast hash is enough, unlike passwords: the id has 256 bits of entropy, so there is nothing to brute-force.

**Q: A user is banned while signed in on two devices. What happens?**
A: `Ban` sets `banned_at` and deletes every `auth_sessions` row of that user, so the next request from either device gets 401. If a ban were written without deleting sessions, `Guard` would still see `banned_at` on the next request, answer 403 and delete them. A new sign-in reaches the callback, finds `banned_at` and redirects to `/signin?error=banned` without creating a session. Tests cover all three paths.

**Q: How would this change with many servers or regions?**
A: Nothing in the session logic depends on one server: the session lives in Postgres, so any replica can check it. The per-IP sign-in rate limit is in memory per replica (at most 2 here); with many replicas it would move to a shared store such as Redis or a Postgres table.
